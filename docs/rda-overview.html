Repository Dependency Analyzer

Next-generation specification — an internal web tool that reads the package.json files of many Git repositories — monorepos included — and consolidates every declared dependency into a single interactive graph, with explicit detection of version drift: the same package pinned to different version ranges in different projects.

DRAFT SPEC — next-gen, new repository

What is RDA

RDA answers two questions in seconds: "which dependencies does this repository declare?" and "which projects use this dependency, and on which versions?". It works against GitHub and GitLab (including self-hosted instances), reads every package.json in a repository — not just the root one — and presents the result as an interactive graph of repositories and packages. The graph is the only view, by design.

There is no backend database: access tokens live only in memory during the session, and the only thing persisted is the repository list (provider, host, path, branch) in the browser's localStorage. All communication with Git providers flows through server-side proxy routes inside the same Next.js app, which avoids CORS issues and keeps token handling centralized.

Changes vs v1

  • Graph-only UI. The dependency list/panel stage is gone from the critical path — analysis results exist as the graph and nothing else.
  • Canvas-first UI. The header+sidebar chrome is gone too: the graph canvas fills the app, with floating React Flow Panels for tools (add repository, manage tokens) and for the repository list.
  • Highlight rides React Flow's native selection. Click-to-highlight uses the library's built-in selection model (selected node property, onSelectionChange, native shift-click multi-select) instead of custom click state — the list panel constrains itself to single selection, the canvas keeps native multi-selection.
  • Detail sheets open via an icon on each node. Selection stays reserved for highlight; a small icon in the node's corner opens the repo's dependency sheet or the package's drift sheet.
  • Unbounded repo palette. Accent colors are generated per repo with no 8-color cap.
  • Softer dim. Unrelated nodes/edges dim to 50% opacity during highlight (was 20%).
  • Leaner package set. p-limit, d3-force, sonner, and lucide-react are out (see Packages).

End-to-end flow

1. Configure tokens→ 2. Add repositories (paste URLs)→ 3. Pick a branch per repo→ 4. Click Analyze→ 5. Explore the graph

Steps 1–3 are one-time setup per session (tokens are re-entered each session; repos and branches survive reloads). Step 5 is the daily loop — clicking repo nodes opens their dependency sheets, clicking package pills opens drift details.

Access tokens

Behavior

  • The Access Tokens dialog (opened from Manage tokens in the canvas tools panel) accepts one GitHub PAT and one token per GitLab host — gitlab.com is always listed, and each self-hosted host appears automatically once a repo from it is added.
  • Tokens are never persisted. They live only in an in-memory store (no localStorage, no cookies). Reloading the page wipes them, and the dialog says so explicitly: "Tokens are kept in memory only and never stored." Password fields use autocomplete="new-password" so the browser's password manager won't offer to save them either.
  • No silent fallback: a GitLab repo on a host without a configured token is blocked — operations show a "token needed" hint instead of trying another token.
  • Clear all instantly drops every token; subsequent API calls fail with 401 and the UI points back to the dialog.
  • Tokens travel only as an HTTP header to the app's own same-origin proxy, which converts them to each provider's format (Authorization: Bearer for GitHub, PRIVATE-TOKEN for GitLab). They never appear in URLs or logs.

Repository management

Behavior

  • Adding a repo is pasting a URL (https://github.com/owner/repo, https://gitlab.com/group/sub/project, self-hosted equivalents, with .git and /tree/...//-/tree/... suffixes tolerated). The URL is parsed and validated client-side before any request.
  • The provider is detected from the hostname: github.com → GitHub; anything else → GitLab (which also enables self-hosted instances).
  • Token gate: without the applicable token, adding is blocked with a toast and nothing is saved.
  • On success, the app fetches the repo's default branch and stores the repo in localStorage (key rda-repos) — provider, host, path, branches only, never tokens or fetched data.
  • Dedupe: re-adding the same provider+host+path doesn't create a duplicate; it selects the existing card (GitHub paths compare case-insensitively).
  • Each repo is an item in the canvas-side repository list panel: name in monospace, provider badge, host badge for non-gitlab.com GitLab, a branch selector, and a remove button. List items are selectable (single selection within the list, keyboard-accessible) and the selection survives reloads; clicking an item has the same effect as selecting that repo's node on the canvas (see Graph view). Removing a repo drops it from the next analysis.

Branch selection

Behavior

  • Each card has its own branch dropdown, loaded on demand from the provider (paginated, capped at 500 branches) and cached per repository.
  • The chosen branch is persisted per repo and restored on reload; repos keep independent selections.
  • Switching branches re-reads that repo's package.json files on the next Analyze — each repo+branch pair is cached separately.
  • If the persisted branch was deleted upstream, the selector shows it as a disabled "(not found)" option so the user understands the 404s instead of seeing a blank box.
  • States: skeleton while loading, destructive badge on error, amber "token needed" badge when no token is configured.

Repository scanning

Behavior

  • Analysis scans each repo's entire file tree on its chosen branch and reads every package.json — the monorepo-aware part. Generated directories are excluded: node_modules, dist, build, .next, out, coverage, vendor.
  • File downloads run with bounded concurrency (8 at a time) to stay friendly to provider rate limits. A malformed or failing file is skipped and counted — it never aborts the rest.
  • Dependencies are classified as Dependencies / Dev / Peer, and version ranges are kept as raw strings (^18.2.0, workspace:*, etc. — no semver interpretation).

Cross-repo analysis (Analyze)

Behavior

  • One click on Analyze aggregates every registered repo at its selected branch. The button is disabled with no repos or while running.
  • Grouping is dependency → version range → projects: each package becomes one entry; each distinct range string a group; each group lists the projects declaring it. A monorepo's packages count individually, and ^1.2.3 vs 1.2.3 are deliberately different ranges — the goal is literal manifest divergence, not semver resolution.
  • Groups sort drift-first (more than one distinct range), then by project count.
  • Partial failures never abort: a repo without a token, a 404, a rate limit, or a network error lands in a dismissible amber banner naming the repo and reason; the rest complete normally. If everything fails, the banner says so explicitly and no results render.
  • The analysis reuses the warm cache (5-minute freshness window) — repos read moments ago cost zero new requests.

Graph view (the only view)

After Analyze, results render directly as an interactive force-directed graph. This is the app's single view for analysis results — and the app is canvas-first: the graph fills the window and every tool floats over it.

Layout & chrome (React Flow Panels)

  • No header or sidebar: the canvas occupies the full app surface. Utilities live in floating Panel components (React Flow's native overlay primitive, anchored to canvas corners).
  • Tools panel — buttons for Add repository, Manage tokens (opens the Access Tokens dialog), the dependency-type toggles, and Analyze.
  • Repository list panel (side: left or right, TBD) — the list of registered repos with their branch selectors. It mirrors canvas selection: clicking a list item selects the corresponding repo node and applies the same highlight as canvas selection. The list enforces single selection; the canvas keeps React Flow's native multi-selection (shift-click / selection box) — both behaviors come from the library, nothing custom.
  • Standard canvas controls (zoom, pan, fit) via Background + Controls.

Nodes

  • Repository nodes — rectangles with the repo name and evaluated branch. Each repo gets a distinct accent color generated without a palette cap (derived deterministically from the repo identity, e.g. hash-based hue rotation), used for its border and its outgoing edges.
  • Package nodes — pills with the package name, an amber drift marker when version ranges diverge, and one version badge per using repository, each badge colored with that repo's accent color.
  • Layout — force-directed: packages used by multiple repos accumulate link attraction and settle near the center; unique packages dangle near their parent repo. Positions are deterministic (same input → same layout), computed synchronously by the app, and recomputed when the visible set changes.
  • Edges — straight lines in the source repo's color. Handles sit at each node's center, so edges visually attach from any direction (and are non-interactive, so they can't start a connection). Node dragging is disabled.

Interactions

  • Highlight = React Flow native selection. Clicking a node (repo or package) selects it via the library's built-in selection model (selected property on the node, surfaced through onSelectionChange; multi-select via shift-click and selection box comes free). The highlight rule derives from that state: selected nodes, their direct neighbors, and connecting edges stay fully visible; everything unrelated dims to 50% opacity. Deselecting (click the node again, click the pane, or press Escape — all native) clears it. Selecting from the repository list panel produces the identical effect, constrained to one repo at a time.
  • Sheet icon on every node — each node carries a small inline-SVG icon in its corner (an inline-SVG button; no icon library) that opens its detail sheet on click, without disturbing the selection/highlight state:
    • Repository node → sheet with a table of everything that repo declares: package, version, and drift status, with a package-count badge in the title and monorepo paths shown for non-root manifests.
    • Package pill → sheet with the drift table: every project using the package, with repository, target branch, declared version, and a status column (aligned / most common / divergent). The title shows the package name with a badge counting distinct versions.
  • "Show shared only" checkbox → hides packages connected to a single project and recalculates the layout with what remains.

Failure handling

  • Partial failure is a first-class state everywhere: per-file (skipped + counted), per-repo (banner), per-host (one unreachable GitLab doesn't affect others).
  • Errors map to actionable messages: 401 → review your token; 404 → repo not found / no access; 429 (and GitHub's 403 rate-limit body) → rate limit, try later; network failure → 502 with a JSON body from the proxy.
  • No API error crashes the current view; transient feedback (toasts) is paired with inline badges where a component is affected.
  • Pagination loops are capped (5 pages of branches, 100 pages of tree entries) so a misbehaving upstream can't spin forever, and proxy calls have a 30-second timeout.

Architecture

Request path

UI (React)→ TanStack Query cache→ HTTP client (injects token headers)→ /api/proxy/github/* or /api/proxy/gitlab/*→ GitHub API / GitLab instance
  • The browser never talks to Git providers directly. Two Next.js Route Handlers proxy everything: the GitHub one targets a fixed host; the GitLab one reads the target host from a header and validates it with an anti-SSRF guard (http/https only; rejects localhost, private/reserved IPs including IPv6 forms, embedded credentials) and never follows redirects.
  • Proxy responses are passthrough with no-store both ways — caching lives exclusively in the client.
  • Provider differences (URL parsing, pagination style, base64 vs raw file content) are isolated behind one interface, so the data layer is provider-agnostic.
  • State: lightweight client stores — repos + selection (persisted), tokens (memory-only), UI settings (persisted), and ephemeral analysis results.

Packages

The three pillars

@tanstack/react-query v5

Owns all server-state caching. Query keys isolate every combination: ['branches', repoId] and ['pkg-files', repoId, branch] — switching repos or branches never reads another entry's cache. Defaults: 5-minute staleTime (exploration without refetch storms), 30-minute gcTime, one retry, no focus refetch. Analyze orchestration uses ensureQueryData so it reuses anything warm, and query concurrency is managed through TanStack Query itself — no separate concurrency library.

shadcn/ui new-york / neutral

The entire component vocabulary: button, input, badge, card, checkbox, dialog, select, skeleton, separator, scroll-area, sheet, table. Components are used as shipped — styling is composed with className at usage sites (amber warning styling, monospace identifiers), never by editing the generated internals. Only the base components are adopted; auxiliary libraries previously layered around them (toast and icon packages) are out of scope.

@xyflow/react (React Flow) v12

Powers the graph view end to end: custom node components (repo cards, package pills) registered via nodeTypes, centered non-interactive Handles for the attach-from-any-direction edge look, type: 'straight' edges, and Background + Controls for the canvas chrome. App chrome uses the library's native primitives instead of custom UI: Panel for the floating tools and repository-list overlays, and the built-in selection model (selected node property, onSelectionChange, native shift-click multi-select and selection box) drives the highlight behavior — no custom selection state. Detail sheets open from an inline-SVG icon on each node. The canvas itself stays close to the documented default pattern — plain memoized nodes/edges arrays — with nodesDraggable off.

Known limits

  • Branch selectors cap at 500 branches per repo; GitHub's recursive tree may truncate on giant repos (tolerated — coverage can be partial without error).
  • Node dragging in the graph is disabled.
  • Drift is a literal string comparison of version ranges, not semver equivalence.
  • Desktop-first (≥1280px); below 1024px the layout degrades to a stacked scroll.
